# Controlled Codex runtime distribution

The optional `codex-controlled-runtime` component installs a qualified, content-pinned runtime bundle from `iryzhkov/codex`. The closed manifest pins a `controlled-v<upstream>-rc.<n>` release tag, exact source commit and tree, and explicit host list. For each supported target (`x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`) it pins the archive basename and SHA-256 plus the matching receipt basename and SHA-256.

The receipt contract is `codex-controlled-runtime-receipt-v1`. Its repository, tag, source commit, source tree, target, archive name and archive digest must match the component. Compiler provenance and both rusty-v8 hashes must be present. Capture verifies that `SHA256SUMS` covers both archives and both receipts, verifies every receipt digest, and validates every receipt against the authored source identity. It does not claim that `codex --version` proves a source commit.

Targets download only their archive and receipt through their existing GitHub authentication. The adapter bounds compressed and expanded sizes, rejects absolute, non-clean and traversing paths, rejects links and special members, and accepts only regular directories and files. It requires an executable `bin/codex` and a closed `codex-package.json` identity with layout version 1, variant `codex`, the exact target, and entrypoint `bin/codex`.

The whole bundle is installed under a content-addressed directory in `~/.local/share/codex-controlled/releases`. The retained archive is checked against the manifest and used to compare every installed file and mode during observation. Activation atomically switches only `~/.local/bin/codex-controlled` to the versioned `bin/codex`; the normal mise-managed `codex` shim is never read or written. Failed verification restores the prior dedicated link, while a concurrent link change is preserved for manual recovery. Supported convergence is serialized at `converge.Fleet` by `locks.Store.Acquire` for the host before the component runner starts; its integration test verifies that a second convergence reports `lock-contention` and never invokes the runner. The component also revalidates the dedicated link immediately before rename, but does not claim a conditional filesystem replacement against arbitrary external writers.

This component is absent by default and carries no credentials or T3 provider configuration. Older manifests remain valid because it is optional. Older UpKeeper binaries reject the new component name when it is present, so publish and converge the UpKeeper capability before authoring any component pins. Do not capture or add pins until the runtime artifacts have completed qualification.
